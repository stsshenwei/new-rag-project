## 背景

后端当前会构造 `DoclingDocumentParser`，将输出规范化为 `ParsedElement`，按 H1/H2 对章节分组，并依据估算的 token 长度切分超长文本。现有实现中，预期的 Docling 转换路径包含不可达或位置错误的代码，OCR 提取实际上为空，切片器也缺少文档画像、语义边界、受保护区间和质量降级机制。相比之下，当前原始证据架构已经较为完善：SQLite 负责保存文档与切片事实数据，FTS5 和 Milvus 是可重建的派生索引，系统已经支持父块召回，并且分阶段上传任务已经能够维持知识库作用域。

WeKnora 展示了两个有价值且可以彼此分离的设计：一是由 Python 内置解析器服务输出 Markdown 与图片，二是由应用侧负责自适应切片和多模态处理流水线。本设计采用这些边界，但不照搬其 Go、asynq 和 PostgreSQL 部署方式。Bee 继续保持 FastAPI 应用架构，使用 SQLite 持久化任务状态，并将 Milvus 和 FTS5 用于检索，同时保持各种外部能力为可选 Provider。

本变更会影响解析、切片、存储 schema、上传配置、任务编排、处理预览和受控重建行为。实现必须继续保证路径安全、租户与知识库隔离、HTTP 处理器轻量化，并遵守“Provider 失败不能静默改变实际生效行为”的原则。

## 目标 / 非目标

**目标：**

- 将 `builtin` 建设为可靠的默认解析引擎，并明确记录请求引擎和实际生效引擎。
- 使用 `pypdfium2` 解析原生文本 PDF、扫描 PDF 和混合 PDF，重建可用的 Markdown，并保存页面与图片证据。
- 通过低成本文档画像选择标题感知、启发式或递归切片策略，并在输出质量明显不合格时自动降级。
- 通过自适应父子切片分离检索粒度与回答上下文粒度。
- 独立执行 OCR 和图片描述任务，限制并发并支持针对性重试。
- 提供无副作用的处理预览，使解析器和切片器的决策过程可观察、可调试。
- 继续由 SQLite 保存业务事实，将 FTS5 和 Milvus 视为可重建的派生索引。

**非目标：**

- 本变更不引入 Go DocReader 服务、asynq、Redis、PostgreSQL，也不强制使用远程对象存储。
- 不逐项复制 WeKnora 的全部解析器、UI 细节、正则表达式或部署组件。
- 不要求 MinerU、OpenDataLoader、Docling、OCR 或 VLM 成为后端启动的必备依赖。
- 不实现基于语义模型或大语言模型的切片边界检测。
- 知识库切片配置发生变化时，不自动重建所有已有文档索引。
- 不迁移、兼容读取或对外暴露任何旧版持久化数据；启用新架构时直接执行一次性全库清空。

## 技术决策

### 1. 引入解析器注册表，并以 builtin 作为稳定默认引擎

新增 `ParserEngineRegistry`。每个注册项将规范化文件扩展名映射到解析器工厂和可用性探针。解析结果返回结构化选择信息，包括请求引擎、实际生效引擎、解析器名称以及回退原因。对于受支持的格式，`builtin` 始终作为最终可用解析引擎。所有可选引擎都采用延迟加载，避免缺少可选依赖时后端无法启动。

第一阶段，builtin 映射优先覆盖项目当前已接受并且能够充分测试的格式：PDF 使用 `pypdfium2`，DOCX 使用 `python-docx`，Markdown 使用原生解码，Excel 使用 `openpyxl`，图片使用经过校验的媒体读取器。只有在依赖和沙箱行为明确后，才增加旧版 DOC、EPUB 和 MHTML 支持。

备选方案：修复 Docling 并继续只使用一个解析器。否决原因：混合 PDF 路由、稳定回退以及对运维人员公开实际引擎选择，都需要明确的 Provider 边界。Docling 可以继续作为可选注册项存在。

### 2. 使用三遍处理的 builtin 混合 PDF 解析器

PDF 解析器使用 `pypdfium2` 从字节内容打开文档。对于底层 PDFium 运行时中不适合并发访问的部分，进行串行化保护。

第一遍逐页提取文本和图片面积信号，对页面进行分类；仅当普通文本提取质量较差时才重建版面顺序；以保守规则提升视觉标题为 Markdown 标题；移除重复页眉页脚；并提取符合条件的矢量图表区域。第二遍使用独立的有界执行器，仅渲染被识别为扫描页的页面，并应用 DPI、JPEG 质量和最大边长限制。第三遍从原生文本页中提取符合条件的嵌入图片。最后按照原始页面顺序组装 Markdown 和图片引用。

强制扫描模式会跳过页面分类。对于意外的页面路由错误，可以回退为全页渲染；但密码保护、文件损坏、资源超限等错误必须明确返回，不能触发高成本的隐式重试。诊断信息包括页面与图片数量、阶段耗时、警告和稳定错误码。

备选方案一：将全部 PDF 页面渲染后统一执行 OCR。否决原因：速度更慢、成本更高，而且会丢弃可信的原生文本层。

备选方案二：默认优先使用 Docling。否决原因：本变更要求默认路径是确定性的 builtin 混合解析；Docling 仍可作为可选引擎或受控回退引擎。

### 3. 将解析输出规范化为证据丰富的领域模型

扩展 `ParsedDocument`，增加规范化 Markdown、元素集合、图片描述符、元数据和诊断信息。新增 `ParsedImage`，保存稳定 ID、存储键、来源类型、页码、媒体属性、标题和父元素。`ParsedElement` 继续保存标题、页码、版面和图片引用信息。大型二进制内容或 base64 数据不写入 SQLite 领域记录。

图片通过 `ObjectStorageProvider` 写入存储。第一版的本地实现只允许写入配置的安全媒体根目录，并使用系统生成的存储键；未来接入 MinIO、S3 或 COS 时保持同一接口契约。解析结果在文档事务准备完成前保持为暂存状态，并能够清理被取消或遗弃的本地资源。

备选方案：将图片以 base64 写入切片 metadata。否决原因：会造成 SQLite 和 API 响应过大、内容重复以及显著的内存压力。

### 4. 在统一的递归切片基础上实现策略解析器

`DocumentProfiler` 负责生成稳定的文档结构信号。`AdaptiveChunker` 对显式策略直接执行，对 `auto` 策略构建候选链。标题切片器和启发式切片器只负责发现、组织结构边界；超长区域统一交给递归切片器继续处理。`ChunkValidator` 检查非最终策略的输出，拒绝明显不可用的结果并记录原因。递归切片始终作为最终安全兜底。

为兼容选定的 WeKnora 默认参数，切片尺寸明确使用字符单位，配置字段带 `_chars` 后缀。近似 token 数仅作为展示信息；只有配置了嵌入模型 tokenizer 上限时，才额外执行 token 限制。普通切片默认目标为 512 字符、重叠 80 字符；父子模式默认父块 4096 字符、子块 384 字符，子块重叠约为 20%。质量验证将目标尺寸的两倍视为警戒或拒绝阈值，而不是所有场景下的绝对硬上限。

备选方案：继续使用 `max_tokens * 4`。否决原因：现有 API 将配置命名为 token，实际却按字符执行，对参数理解和中文内容都会产生不可预测的结果。

### 5. 使用受保护区间和表头重复机制保护文档结构

切片前扫描围栏代码块、公式、图片引用、链接以及 Markdown 表头和表格行，并生成受保护区间。位于受保护区间内部的标题边界或启发式边界将被忽略。普通装箱过程中将受保护单元视为原子结构；当单元超过安全上限时，允许在换行或空格边界强制拆分，以保护嵌入模型和内存限制。表格行跨多个切片时，在后续切片的嵌入上下文和 LLM 上下文中重复表头，但不伪造或改变原始内容偏移。

现有独立 `table` 切片对结构化检索仍有价值。解析器和切片器会从规范化表格元素创建这些切片，并复用统一的来源信息与保护模型，避免继续维护一套互不兼容的平行表格处理流程。

### 6. 在父块和子块两个层级都运行自适应策略

启用父子模式后，先使用父块目标尺寸对文档执行自适应切片，再对每个父块使用子块目标尺寸单独执行画像和切片。父块保存在 SQLite；`child`、`table`、`image_ocr` 和 `image_caption` 是可索引类型。检索结果保留子块身份，并按知识库作用域召回父块作为回答上下文。如果父块只生成一个内容完全相同的子块，则依据确定性规则折叠冗余证据。

`context_header` 或标题面包屑与原始正文分开存储，仅在生成 embedding 上下文或模型上下文时添加。这样可以维持正确的源内容偏移，并避免标题重复。

备选方案：继续按 H1/H2 创建父块，再对父块硬切子块。否决原因：这种方式会在最影响检索精度的子块层丢失自适应行为。

### 7. 将 OCR 和图片描述视为可独立重试的派生证据

文本解析和切片成功持久化后，根据实际生效的 OCR 与图片描述设置创建图片处理操作。Provider 返回生成文本及其置信度和 metadata；成功结果会成为独立的图片派生切片，并关联图片、页面、文档和最近的文本父块。Provider 错误只更新对应图片操作及任务阶段，不影响已经成功的文本证据。独立并发预算确保大型扫描 PDF 不会耗尽普通解析工作线程。

第一版继续使用现有进程内执行器和持久化任务表。任务阶段接口按照队列形态设计，包括 `parse`、`chunk`、`index`、`multimodal` 和 `postprocess`。未来可以替换为外部 Python 任务队列，而无需修改上传 API 契约。

备选方案：立即引入 Celery。否决原因：当前可以先在不增加 Redis 运维负担的情况下实现持久化生命周期和 Provider 隔离。

### 8. 预览复用生产决策路径，但禁止提交数据

处理预览复用相同的注册表、解析器、画像器、切片器和验证器，但运行在禁止提交的上下文中，并使用受限的临时资源。预览不得调用 embedding、FTS、Milvus、KG、知识增强或文档发布逻辑。响应返回实际生效配置、解析诊断、文档画像、策略尝试轨迹、完整切片集合的统计信息和数量受限的切片样本。预览的时间、页数、文件大小、渲染量和响应大小限制应比正常导入更加严格。

备选方案：为预览单独实现一套轻量算法。否决原因：预览与正式导入之间的算法差异会使配置调优结果失去可信度。

### 9. 对新 schema 进行版本化，并在切换时执行一次性全库清空

本次技术架构变更不兼容任何旧版持久化数据。启用新版本前必须通过显式维护命令执行一次性全库清空，包括：删除整个旧版 SQLite 数据库及其中全部认证、租户、工作区、知识库、文档、切片、任务、会话、记忆、知识图谱、评测和 FTS 数据；删除全部 Milvus collection 与向量数据；删除旧版媒体文件、图片资源和其他派生处理状态。系统不提供旧数据读取、迁移、转换、查询或展示接口。

全库清空完成后，应用使用最终 schema 从空状态初始化 SQLite 和 Milvus。正常启动不得隐式执行清库；如果检测到旧 schema 或未完成清理的旧 collection，启动进入 `reset_required` 维护状态，拒绝正常读写，直到管理员明确执行全库重置命令。重置命令必须要求显式确认目标环境，输出将被删除的存储范围，并在执行后验证 SQLite、Milvus、FTS 和媒体目录均已清空且新 schema 可以初始化。

备选方案一：原地迁移旧 SQLite 和向量记录。否决原因：解析方式、切片内容、chunk ID、embedding、任务模型和数据边界均已改变，迁移会增加长期兼容负担并可能混入不可信旧证据。

备选方案二：只清理 RAG 派生数据，保留认证、会话和记忆数据。否决原因：本次决策要求新架构从完全空的应用数据库启动，任何旧版业务记录都不继续保留或暴露。

## 风险 / 权衡

- [PDFium 线程或进程安全问题、原生库崩溃] → 对不安全的 PDFium 区域串行化，限制并行渲染，确定性关闭原生句柄，并增加混合 PDF 和并发 PDF 测试。
- [标题重建产生错误结构] → 使用保守的字号和版面阈值，公开诊断信息，验证切片输出，并允许降级到启发式或递归策略。
- [OCR 密集型 PDF 消耗过多 CPU、内存或 Provider 配额] → 限制页面数、文件大小和图片边长，分阶段渲染，使用独立并发预算，并且仅在显式配置时启用强制扫描。
- [本地图片存储积累遗弃文件] → 使用系统生成并带作用域的存储键，持久化资源所有权，取消任务时清理，并测试删除与重建流程。
- [受保护区间产生超长 embedding 输入] → 限制保护区间最大长度，执行安全强拆，遵守 Provider token 上限，并输出警告。
- [字符默认值在不同语言和嵌入模型中表现不同] → 明确配置单位，保留可选 token 上限，增加中文测试样例，并显示实际尺寸统计。
- [父块扩展造成上下文重复] → 按带作用域的父块 ID 去重，同时保留子块证据用于引用和排序。
- [OCR/VLM 生成内容被误认为原始文本] → 保留生成证据类型、Provider、置信度和源图片关系，绝不将生成文本合并进原始父块正文。
- [全库清空不可逆且会删除所有用户和业务数据] → 仅允许通过显式维护命令执行，要求环境与删除范围确认，执行前由运维自行完成需要的外部备份，并在命令输出中明确不可恢复；正常启动和普通 API 永不触发清库。

## 迁移计划

1. 在隔离的开发和测试环境完成新领域模型、注册表、builtin 解析器、存储 Provider、文档画像、切片器、预览能力和最终 schema。
2. 实现独立的全库重置维护命令，覆盖 SQLite 数据库文件或全部表、FTS、全部 Milvus collection、旧媒体目录和派生处理状态，并加入目标环境、删除范围和显式确认保护。
3. 停止旧版 API、后台 worker 和所有可能写入 SQLite、Milvus 或媒体目录的进程。
4. 由运维决定是否在系统外部保留冷备份；新应用不读取、不迁移、也不暴露该备份。
5. 显式执行全库重置命令并验证所有旧数据均已删除。
6. 从空状态初始化最终 SQLite schema、FTS 和 Milvus collection，然后启动新版本。
7. 使用全新的租户、知识库和安全测试文档执行解析、切片、索引、检索和删除冒烟测试。

回滚不包含应用内数据恢复。若运维事先制作了完整外部快照，只能通过基础设施级恢复旧应用与整套旧存储；新版应用永远不得读取或解释旧版 SQLite、Milvus collection 或媒体数据。
